# Design: Postgres + pgvector as a second store

## Why
Today everything is stored in SQLite (passages and FTS5 keyword index) plus one
numpy file of vectors. That is right for a laptop: no setup. A real deployment
would use a database server that several API processes can share, that filters
and ranks inside the database, and that has a proper index for vectors. This
adds Postgres with the pgvector extension as a second store, chosen by a
setting. SQLite stays the default.

## Goals
- `PgStore` offers the same methods as `Store`, so search, ingest, eval and
  the API work unchanged on either.
- One setting picks the store: `--index` / `FILING_ANALYST_INDEX` holds either a
  folder (SQLite, as today) or a `postgresql://` address.
- One shared set of storage tests runs against both stores, so any difference
  in behaviour fails a test.
- The real filings are ingested into both stores and the eval is run on both,
  so the README can show the two side by side.

## Non-goals
- Database migrations (Alembic). The index is rebuilt from the filings by
  `ingest`, so the schema is created fresh each time.
- Updating only some filings. `ingest` replaces everything, as today.
- A connection pool. The API already lets one request use the store at a time.

## Anti-goals (would be a failure even if it works)
- SQLite users need anything new: no new required packages, no database server,
  and the normal test suite runs without Postgres.
- A database password shows up in a log line, an error message or `/health`.
- Postgres quietly returns fewer results than SQLite when filters are used.

## Approaches considered
- **Plain SQL with psycopg (chosen).** A `PgStore` class with hand-written SQL.
  The two hard parts, keyword and vector search, are different in each
  database anyway, and plain SQL is easy to read and explain.
- SQLAlchemy. One code base in theory, but the hard parts still need separate
  code per database, and it hides the SQL.
- ParadeDB `pg_search` for BM25. Its scores would match SQLite's, but it is a
  niche extension. Plain Postgres + pgvector is the common setup.

## How it works
**Choosing the store.** `open_store(location)` in `store.py` returns `PgStore`
for addresses starting `postgres://` or `postgresql://`, and `Store` for
anything else. The CLI, the API and the tests call `open_store` rather than
`Store`. `describe_location()` prints a store's location with any password
replaced by `***`, for logs and messages.

**Schema** (made by `replace_all`, inside one transaction):
- `chunks`: the same columns as SQLite, the same ids (1..n, in ingest order, so
  eval results can be compared), plus:
  - `embedding vector(D)`, where D is taken from the vectors being saved;
  - `tsv tsvector`, generated by Postgres from `text` and `section` with the
    `english` configuration (stemming, like SQLite's `porter`).
- A GIN index on `tsv` for keyword search, and an HNSW index on `embedding` with
  inner-product distance (vectors are already normalised, so inner product
  equals cosine).
- `meta(key, value)` for the embedder name.

**Keyword search.** The same `fts_query` word list (only letters and digits, so
no search syntax can get through), joined with `|` (OR) and passed to
`to_tsquery('english', ...)` as a parameter. Ranked by `ts_rank_cd`. This is
not BM25, so keyword scores and eval numbers will differ from SQLite. That is
expected, and the eval comparison reports it.

**Vector search.** `ORDER BY embedding <#> query LIMIT k`, with company and year
as a `WHERE` in the same query. HNSW with a filter can return fewer than k rows,
because it finds the nearest rows first and filters afterwards. pgvector 0.8
fixes this with `hnsw.iterative_scan`, which this store turns on. A test checks
that a filtered search returns all k matching rows.

**Connections.** One psycopg connection per store, with autocommit for reads. The
API's existing lock already serialises store use.

**Running it.** `docker-compose.yml` gains a `db` service (image
`pgvector/pgvector:pg17`) in a `postgres` profile, so plain `docker compose up`
is unchanged. Its password comes from `.env`, its port is published on
127.0.0.1 only, and its data is kept in a named volume.

**Packages.** A new optional extra, `postgres = ["psycopg[binary]", "pgvector"]`,
also added to `dev`. SQLite users install nothing new.

**Tests.** The storage tests run once per store. The Postgres run is skipped
unless `FILING_ANALYST_TEST_PG` holds an address. The tests always use a
separate database, so a run can never wipe a real index.

## Left to the builder
- Whether `/health` reports which store is in use (yes, as `store: "sqlite" |
  "postgres"`, never the address).
- Exact index settings (HNSW defaults are fine at this size).
